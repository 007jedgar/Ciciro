# Agent instructions

## Merge conflicts

Resolve PR / branch conflicts by **rebasing** onto the base branch. Do not merge `main` (or `master`) into the feature branch to clear conflicts.

- `git fetch origin && git rebase origin/main` (or the PR's base branch)
- Never `git rebase -i` (no interactive rebase)
- After each conflict: edit, `git add`, `git rebase --continue`
- Already-pushed branch: `git push --force-with-lease`
- Never force-push `main` / `master`
- If a rebase is in progress, finish or abort it — do not start a merge

## Screenplay page engine

`src/lib/screenplay.ts` (no imports; mirrored byte for byte to `apps/mobile/lib/screenplay.ts`, `test/screenplay-parity.test.ts`) owns the screenplay element model and the fixed page (12pt Courier, 60 columns, 54 lines): `layout`/`paginate`/`estimatePages` (exact, with `(MORE)`/`(CONT'D)` rows, dual-dialogue pairs and scene numbers from `PageOptions`), the structure helpers, the script-settings helpers and the tag helpers. `manuscript-kind.ts` re-exports the element model. A script stays flat `<p data-sp="...">` blocks; the web editor's `ch` CSS in `globals.css` mirrors `ELEMENT_METRICS` (`test/screenplay-css.test.ts`), and the page markers, the header's "N pages" and the PDF all call this one layout, so change the numbers there and regenerate the golden (`test/fixtures/screenplay`, `UPDATE_GOLDEN=1`). Store the `data-sp` tag, never the collapsed element (`elementTag`/`elementTagOfHtml`, `withElement(html, tag)`): both clients rewrite blocks on every edit, so collapsing an unknown element to action would strip a newer client's; the same goes for `data-sp-dual` on a cue (`dualOfHtml`/`withDual`, which the phone's `restampCiciroHtml` must carry). A script's own settings (title page, `(MORE)`, `(CONT'D)`, scene numbers) are one JSON string, `Project.scriptSettings` (`prisma/d1-script-settings.sql`), shaped and tidied only by `parseScriptSettings`/`serializeScriptSettings`: a new setting is a key there, not a column. The screenplay PDF (`src/lib/export/screenplay-pdf.ts`) draws `typesetSequences`, never its own layout, so its page count is the editor's; Fountain (`src/lib/fountain.ts`) and FDX (`src/lib/fdx.ts`, labelled "FDX export", never "Final Draft compatible") are interchange only and web / server only. Script formatting covers English and Spanish: a script control that cannot work in another language is grayed out with an info button (`ScriptLanguageInfo`, `screenplay.languageInfo.*`), never hidden. Shortcuts are Alt+Shift+1 to 8 (and D for dual dialogue), never Cmd/Ctrl+digit. Screenplay is Beta: mark it wherever the author meets the formatting. The assistant reads and writes a script as marked lines (`SCRIPT_FORMAT`, `markedLine` / `parseScriptLines` / `scriptDisplayText` in `manuscript-kind.ts`, mirrored to the phone and compared in `test/script-lines.test.ts`; `script-view.ts` is what the model reads and `passages.ts` makes each scene heading a passage): any prompt or path that hands script text onward goes through that contract, never raw HTML or bare lines. The phone's page view (`apps/mobile/lib/script-pages.ts`) sets the same `typesetSequences` rows the PDF draws; do not write a second layout. Writing speed (capitals as typed, the name / place / time index and its completions, `smartTab`, cue extensions, `continuesSpeech`, `sceneOutline` / `moveSceneOrder`) is also decided in `screenplay.ts`: the web popup (`tiptap-screenplay.ts`) and the phone chips (`lib/screenplay-speed.ts`) only carry it out, and the phone passes `trailing: false` because the chapter text drops a trailing space on commit; see `docs/screenplay.md`. Kind-specific settings live in a section at the top of Settings, only while that manuscript is open (`hasKindSettings`; web `ManuscriptSettings`, phone `KindSettingsGroup` via `/settings?project=<id>`). See `docs/screenplay.md`.

## Project canvas (mobile)

The canvas (`src/components/CanvasBoard.tsx`, `src/lib/canvas.ts`, `src/lib/canvas-view.ts`) is view-only on the phone: `app/project/[id]/canvas.tsx` fetches the same `GET /api/projects/:id/canvas` the web uses (existing session auth, no webview or token bridge) and renders cards, labels and arrows at their stored positions with pan and pinch-zoom, tapping a card into a `GlassSheet` for its full text. `apps/mobile/lib/canvas.ts` is *not* a byte-for-byte mirror of `src/lib/canvas-view.ts` like the files in "Code the phone shares" above: it holds only the rendering-relevant subset (label colors, card width, `curveBetween`, bounds/fit-view math) plus its own types, because the rest of `canvas-view.ts` is outline-generation reply parsing that pulls in `state-review-view.ts`'s chat/drafter stack, which has no mobile surface yet (no card creation or Ciciro generation on the phone). If mobile gains outline generation, mirror that parsing then rather than now. The board's `world` view is sized to its content with `transformOrigin: [0, 0, 0]` because `fitCanvasView` assumes a top-left origin: a zero-size world with a `"left top"` string drew the board far from where the fit put it. Scan notes adds cards here (`app/project/[id]/scan-notes.tsx`), so the phone's board is no longer only for cards made on the web. New routes under `app/project/[id]/` need a `<Stack.Screen>` entry with `CONTAINED_POP_OVER_STACK_SCREEN_OPTIONS` in that folder's `_layout.tsx`, or `project-stack-layout.test.tsx` fails.

## Scan notes (mobile)

Photos of handwritten or printed notes become text the writer checks and then adds to the story bible or the canvas (`app/project/[id]/scan-notes.tsx` → `components/ScanNotes.tsx`, one page per step; the pure rules in `lib/notes-scan.ts`, the camera / library / resize in `lib/notes-scan-capture.ts`, no mirror needed). The server reads, `src/lib/scan-notes.ts` (+ pure `scan-notes-view.ts`) via `POST /api/projects/:id/scan-notes` (`EDITOR_MODEL`, one model call per photo in parallel, one `meterAiRun` per scan, refunded when nothing could be read) and adds, via `.../scan-notes/apply` (free, add-only). Reads use structured output (`output_config.format` json_schema), never a forced `tool_choice`: the 5.5 models reject `type: "tool"|"any"`, and mocked tests cannot catch that, so check any new vision or structured call against the real API once. "Outline" in this feature means canvas cards (`placeOutline`, 200-card cap), never chapter summaries: scanning into chapters is deliberately out of scope. A bible append is a dated `## Scanned notes (YYYY-MM-DD)` section placed before a character file's `<!-- knows:start -->` mirror; a new character / plot line joins an existing file only when its `# Title` names the same entry (`isEntryFor`), and otherwise takes the next free path from `newEntryPaths` (which keeps non-Latin letters, so 张三 and 李四 never share `unnamed.md`), never `createNamedBibleFile`, which would overwrite it. Photos are held in memory for one request and never stored or logged, and the phone deletes its cache copies (`discardPhotos`); keep it that way. The `expo-image-picker` plugin in `app.json` carries the camera / photo-library usage strings, so a change there needs a new native build. A multipart upload from the phone must append an `expo-file-system` `File` (`form.append("page", new File(uri), name)`), never React Native's `{ uri, name, type }` descriptor: the app's global `fetch` is expo/fetch, which throws "Unsupported FormDataPart implementation" on a descriptor (jest cannot see this, only a device can; `lib/import.ts` had the same bug).

## Pre-signup onboarding (mobile)

Between the welcome screen's "Create" and signup sits a mobile-only quiz: `app/onboarding/goal.tsx` (kind, `MANUSCRIPT_KINDS`) → `obstacle.tsx` (one or more obstacles, `lib/onboarding.ts`'s `OBSTACLES`; "Not sure yet" stands alone) → `look.tsx` (Pick a look) → `demo.tsx` → `exercises.tsx` (only when "creativity" or "block" is among the obstacles: it lists the writing exercises and where to find them, and starts nothing, since an exercise needs an account) → `reminder.tsx` (only when "consistency" is among the obstacles) → signup. They share one navigator and one shell (`app/onboarding/_layout.tsx`, `components/onboarding/OnboardingShell.tsx`) that owns the header (back, the thread, Skip), the row of answer chips and the wash scope, so none of it re-mounts between steps; a screen tells it its step, back and Skip through `OnboardingFrame` (or `useOnboardingChrome`). The demo is whichever of the three AI-free demos `demoForAnswers` maps the answers to (most obstacles' vote, ties to the first tapped; `components/onboarding/FocusDemo.tsx` is the real `ChapterEditor` on a page of prose you can scroll and type in, `SuggestionsDemo.tsx` the real `SuggestionsReview`, `ScreenplayDemo.tsx` the real screenplay editor - element-aware formatting, auto-caps, `ScreenplayBar` - on a seeded scene), against throwaway local state - no AI or server call anywhere. Kind overrides the obstacle vote for the two kinds that need a specific page: journal never shows invented sample content (it always gets Focus, on a blank page) and screenplay always gets `ScreenplayDemo` (focus mode is still reachable from inside it, since that is a generic writing feature, not a kind-specific one). The "carry" (`lib/onboarding-shell.tsx`, `CarryOverlay.tsx`): the card tapped on goal, each ticked obstacle on Continue, the shown theme on Continue and the Create reminder button fly into a chip (`useCarry` measures the card, a floating copy in the shell animates over `CARRY_MS` while the screen fades, the push follows `CARRY_PUSH_MS` in). The shell owns the chips (`lib/onboarding-story.ts`); showing a step again takes back its chips and every later step's, and Reduce motion skips the flight (the chip fades in). A new answer that should show in the header goes through `useCarry().fly` with a `CarryLook` (`carry-looks.tsx`), and its caller pushes (and tracks) only when `fly` resolves true (false: a carry was already in the air, or the screen was left mid-flight by a hardware back or edge swipe). The nested navigator sits under the root's single `onboarding` route, so `backOr` only pops it when the root has a screen below (always true from Welcome). Every screen has a Skip straight to signup, and every screen shows the `OnboardingThread` (steps from `stepsFor` in `lib/onboarding-flow.ts`, which also owns the route params and `pathAfter`, the one place a step learns where the flow goes next; a conditional step is added to `ONBOARDING_STEPS` and `stepsFor`, never hard-coded into the screen before it).

Nothing is persisted until signup creates an account. The answers and the held reminder (device-local, scheduled by `WritingReminderSync`) travel as route params; the previewed theme does not, it lives only in memory (`useThemePreview`: the app wears it but it is never cached or synced, so signing in to an existing account cannot overwrite that account's settings) and is the single source of what gets adopted. `AuthScreen`'s `signedIn` saves the answers on any signup but the theme (`adoptPreview`) and reminder only when the sign-in `created` the account (the email signup always does; the social paths report it, since a social sign-in on that screen can land on an existing account). An abandoned quiz persists nothing. The reminder step asks for notification permission on Create reminder, and a denied answer still keeps the reminder. A theme change anywhere (this step, Settings' `ThemeCard` sheet) goes through `useThemeChange`, a circle that grows from the tapped card and reveals a snapshot of the screen already repainted in the new theme (`ThemeWashScope`, mounted at the root and again inside Settings, which sits above the root as a modal). Signing in or up fades the auth screen out and the manuscripts list in, rising (`lib/auth-arrival.ts`), with the submit button's label crossfading to `InlineDots`. A new demo path needs an entry in `lib/onboarding.ts` and a component; a new obstacle or kind option needs i18n in all four locales plus the matching analytics events in both `analytics-events.ts` copies.

## Selection strip (mobile)

What the writer can do with highlighted text (Comment, Describe, Fix, a passage's Rewrite and Expand, a word's synonyms) is a strip docked over the project header, not a menu hung by the selection: the system callout opens wherever UIKit puts it, over the page, so anything placed near the selection can end up under it, and each row scrolls sideways so nothing can overflow. Stacked, the actions replace the Focus / Listen pills and the synonyms the writing meter (a passage, or a word with no synonyms, covers the pills row only); in focus mode, or with the daily goal off, it is one row (`dockFrame`, from the header's measured bottom edge so the page never moves; only on the manuscript tab). `useSelectionMenu` publishes the model to `lib/selection-dock.ts` and `SelectionDockHost`, mounted by `app/project/[id]/(tabs)/_layout.tsx`, draws it. It opens `SELECTION_SETTLE_MS` after the selection stops changing, and never while a finger is on the editor: iOS sends no selection event during a handle drag (one at the lift), so the editor wrapper in `manuscript.tsx` feeds `onTouchStart` / `onTouchEnd` to the hook, with `TOUCH_GUARD_MS` as a fallback for a touch that never ends; on Android the drag's continuous events keep the timer from firing. The B / I / U / S bubble over a highlight shows only in the "On highlight" format home (`showSelectionBubble`); the Smart header and Always on have the bar.

## Natural voice (mobile Listen)

Listen reads with the system voice (expo-speech) or, once the writer downloads it under Settings, Listening (`app/listening.tsx`), Kokoro running on the phone (`docs/natural-voice.md`, the source of truth for model source, licences, benchmarks and the native build). Who reads is decided in one place, `chooseSpeechEngine` (`lib/natural-voice.ts`): the system voice until a model is on the device, always for a language with no natural voice (Mandarin), and as the fallback when `lib/kokoro-engine.ts` gives up mid-read (`SentenceReader`'s `fallback` carries on from that sentence). Everything native (`natural-runtime-executorch.ts`, `natural-audio-output.ts`, the file system in `natural-model-store.ts`) is `require`d lazily behind a small interface and a guard, so jest, web and an older dev client simply read with the system voice; keep it that way, and never import those packages at module top level. Voice ids are permanent (stored in prefs, carried by analytics); a voice is a `NATURAL_VOICES` entry plus a clip in `assets/voice-samples/` made by `scripts/generate-natural-voice-samples.py` (which refuses a silent clip: a file that exists is not a file that plays) and listed in `natural-voice-samples.ts`. The model runs on react-native-executorch (MIT, with the MIT Phonemis phonemizer) behind `NaturalRuntime` (`load(voice)`, `synthesize`, `release`), pinned to exactly `0.10.5` because its model files have no forward compatibility and `KOKORO_FILES` names the Hugging Face files at `v0.10.0` that match it; the app is iOS 17.0 and Android 26 because of it (`expo-build-properties` in `app.json`). Never swap in a runtime that links GPL code (sherpa-onnx links eSpeak NG; the first build did and was replaced). Which voices exist depends on the runtime (`af_sarah` stands in for sherpa's `af_bella`), so a voice needs a file in `KOKORO_FILES.voices` too (a test pins it). A different model pack needs a new `KOKORO_PACK.id`, since it names the folder and keys every saved sentence. The saved sentences are the author's prose as audio: clear them wherever the account's data goes (`forgetAccountOnDevice`), never sync them, and keep text out of its analytics events. Jest cannot see these native seams, only a simulator can: `react-native-audio-api`'s queue `start()` rejects its own default offset, so the output calls `start(0, 0)` (the first real run threw and Listen silently fell back), and the installer's `join` once collapsed `file:///` to `file://`; the fakes now enforce the same rules, but run Listen once on a device after touching either. Android's lock-screen card is a notification, so it shows only when notification permission is already granted and Listen never asks for it itself. The feature adds native modules, so it ships in a new build, never over the air.

## Patched native editor

`apps/mobile` patches `react-native-enriched-html` (`paragraphSpacing`, both platforms; `onSelectionFrame`, iOS only: the selection's first and last line rects, re-sent as the view scrolls; nothing on the phone reads it now, see "Selection strip (mobile)") through `patch-package` in `apps/mobile/patches/`. `npx patch-package react-native-enriched-html` (diff mode) can silently drop hunks when `node_modules` is already patched from a prior run - reinstall the package fresh (`rm -rf node_modules/react-native-enriched-html && npm install react-native-enriched-html@<version> --no-save --ignore-scripts`) before regenerating, or hand-edit the patch file directly and apply it with `node node_modules/.bin/patch-package` (bare, no package arg) to verify it. Any native change needs a rebuilt dev client.

The patch also carries the screenplay page layout (iOS only, behind the `script-layout` pref in `lib/script-layout.ts`): a paragraph style, `ios/styles/ScreenplayStyle.mm`, that holds each paragraph's `data-sp` tag as a marker beside `AlignmentStyle`'s and lays it out from the `screenplay` prop's JSON, built from the shared engine's `ELEMENT_METRICS`/`SPEECH_RUNS`/`nextElementOnEnter` (`screenplayLayoutConfig()`), so the editor owns no page numbers. In that mode the editor's HTML is the source of the tags (`toEnrichedHtml(html, { elements: true })`, `nativeElements` on `restampCiciroHtml`/`opsFromEnrichedHtml`), `getHTML()` returns them exactly, and a tag it cannot lay out is kept as written. The Gumbo normalizer strips unknown attributes, so `data-sp` is let through in `cpp/parser/GumboNormalizer.c`. Android's view manager only accepts and ignores the prop and `setScreenplayElement` (the generated interface needs them; the checked-in generated files mirror them). See `docs/screenplay.md`, "Writing in the page layout".

The native view treats a changed `defaultValue` (and `setValue`) as a whole-buffer replace that parks the caret at the end of the chapter, so `ChapterEditor` fixes `defaultValue` per chapter and every later write goes through its guarded sync effect; a caller that must rewrite the buffer restores the caret with `setSelection` (see `acceptGrammar` in `manuscript.tsx`).

`ChapterEditor`'s `<EnrichedTextInput key={chapterId}>` remounts a fresh native view on every chapter switch, but `ChapterEditor` itself keeps one React instance, so any effect that captures the native ref (`registerEditor`, used to set `manuscript.tsx`'s `editorRef`) needs `chapterId` in its own deps - gating it on the ref-setter alone runs it once for the whole component lifetime and leaves the screen holding a ref to a long-unmounted view, which makes `flush()`'s `editor.getHTML()` reject forever after the first switch.

## Home-screen widget (expo-widgets)

`apps/mobile/widgets/WritingDayWidget.tsx` runs in a separate, worklet-like extraction: only the single function tagged `"widget"` and passed to `createWidget` is captured for the widget extension's runtime. A sibling helper component defined in the same file (even with its own `"widget"` directive) is out of scope at render time and throws `ReferenceError: Can't find variable: <name>` - inline any shared JSX directly in the tagged function instead of factoring it into a separate component. The widget extension's JS is compiled in at native build time (Xcode's "Bundle React Native code and images" phase), not hot-reloaded by Metro, so a change here needs a rebuild (`npx expo run:ios`) before it shows in the widget gallery preview, and widget changes only reach users with a new native build (never an OTA update). See `docs/mobile-release.md` for the release pipeline.

The widget extension itself ships no layout of its own - babel's `expo-widgets` plugin turns the `"widget"`-tagged function into a source-code string, and that string only reaches the shared app group's storage (`UserDefaults(suiteName: groupIdentifier)`, key `__expo_widgets_<name>_layout`) as a side effect of the main app importing `widgets/WritingDayWidget.tsx` (`lib/writing-widget.ts`'s `publishWritingWidgetSnapshot`, the only caller). Until that import has run once, WidgetKit's placeholder, the Add Widget gallery preview, and the home screen all render the same hardcoded red "No layout found for `<group>::<name>`" box (`EntryView.swift` in `expo-widgets`), regardless of app-group entitlements being correctly wired. So that publish call must run unconditionally on every iOS launch - including signed out, with an all-zero `SIGNED_OUT_WIDGET_SNAPSHOT` - rather than being gated on sign-in or data being ready; gating it is what breaks the widget until first login, not a build or entitlement problem.

## Local dev database

A fresh worktree's `dev.db` (the default `DATABASE_URL="file:./dev.db"`, see `docs/hosting.md`) has no tables until `npm run db:push` runs once - without it `npm run dev` 500s on every `/api/*` route with Prisma's "table does not exist". This is local-only; it never touches production D1 (below).

## Production D1 schema

`prisma db push` never reaches the Worker's D1. A schema change needs a `prisma/d1-*.sql` upgrade (see `docs/hosting.md`) applied to production before merging to `main`; the `main` build fails while D1 is behind (`npm run db:check:d1`). Only add tables and columns there: D1 cannot turn foreign keys off, so rebuilding a referenced table (the only way SQLite drops NOT NULL or changes a type) cascade-deletes its children. Model "no value" with a default instead (e.g. `User.passwordHash = ""` for Apple / Google accounts).

## Prisma on Workers

Each hosted request gets its own `PrismaClient` (`src/lib/db.ts`: one isolate-wide client caused Cloudflare 1101s), and each client's WASM engine stays in memory until `$disconnect()`, about 0.5 MB per request against the isolate's 128 MB. The Worker entry frees it once the body and every `waitUntil` / `after()` have settled, counting a body the runtime stopped reading as done after `QUIET_MS` without a chunk (`src/worker/request-lifetime.ts`); never drop that, or wrap `fetch` in a client of its own. A handler that holds a long-lived stream open after its last query calls `releaseRequestPrisma()` (see `/api/sync/stream`). A stream producer that keeps querying after a client disconnect registers its work with `waitUntilRequest()` (see `/api/chat`), or the request ends at the disconnect and frees its client mid-run.

## Account data

Every Prisma model must be both purged by account deletion and written by the data export (`src/lib/account/`, see `docs/account-data.md`); `test/account-delete.integration.test.ts` and `test/account-export.integration.test.ts` fail when a new model is missing from either. Outside-service cleanup at deletion (Stripe cancel, Apple token revoke) goes in `PRE_DELETE_HOOKS`, not the route. A model no account owns (`BetaSignup`, the landing page's iOS beta list) goes in `UNOWNED_MODELS` (`src/lib/account/delete.ts`) instead.

## Password-attempt rate limiting

`src/lib/auth/rate-limit.ts` is the one limiter for every password check (login, and the password proof in account deletion): call `assertAttemptAllowed` before verifying the password, `recordFailedAttempt` on a wrong one, `clearAttempts` on success. It counts `PasswordAttempt` rows (D1, not in-memory, so it works across Worker isolates) per account+IP pair, per account, and per hashed IP (`docs/hosting.md` has the limits); a new endpoint that checks a password must go through it too. The email-link endpoints (forgot password, resend verification, reset) check no password: they use the per-account cooldown and single-use tokens in `src/lib/auth/email-tokens.ts`, and a completed reset clears the account's attempts. `PasswordAttempt` is required, not optional, like the other `prisma/d1-*.sql` upgrades (see `docs/hosting.md`).

## Mobile releases and push

`apps/mobile` ships through EAS (`docs/mobile-release.md`). `runtimeVersion` is the fingerprint policy, and `.eas/workflows/deploy-production.yml` publishes every mobile push to `main` as an over-the-air update to production users when a production build with the same fingerprint exists (a new build otherwise), so merged mobile JS reaches authors on their next launch. EAS builds and updates read EAS environment variables, never `.env`; `app.config.ts` refuses a release bundle without a hosted https `EXPO_PUBLIC_API_URL`. A server-sent notification goes through `sendPushToUser` (`src/lib/push/send.ts`), which owns batching, receipts and dead-token cleanup; tokens belong to the session that registered them.

## Mobile motion

Pass numbers into Reanimated worklets as arguments or same-scope locals: a default parameter or imported constant used inside one can be missing on the UI runtime. A throw there stops every animation until the app restarts, so if motion "does nothing" on the simulator, read Metro's log and relaunch before debugging the code. The same applies to functions: Reanimated only auto-workletizes the callback passed directly to a hook like `useAnimatedStyle`, not a plain function imported from another module and called inside that callback - give the imported function its own `"worklet"` directive, or it crashes every animation with `[Worklets] Tried to synchronously call a Remote Function`.

Pushed screens slide in (and pop out) in `StackPopTransition`, not through the native stack's `animation`: a transparent-modal presentation, which the collapse-on-back needs, gets a vertical cover from UIKit, never a sideways push. An animation that starts from a screen's mount effect is partly or wholly spent behind the heavy first render, so start it from `useTimingOnFirstFrame` (`lib/use-timing-on-first-frame.ts`), which counts only frames that were drawn, and for a pushed screen from the stack's `transitionEnd`, once the view is on show; an entrance inside a pushed screen waits for that push through `useStackArrival` (`lib/stack-arrival.ts`), not its own mount. Tab slides are `sceneStyleInterpolator`/`transitionSpec` on the `(tabs)` navigator (`lib/manuscript-tab-slide.ts`); progress is signed by side, so direction needs no tracking.

On Android, `useReanimatedKeyboardAnimation()`'s `progress` is boolean (0/1 on the IME inset's visibility), not continuous - a floating IME add-on shorter than a real keyboard (the stylus-handwriting toolbar, voice-typing's compact strip) still pins it to 1. Drive keyboard-reactive UI from the paired `height` value instead, ramped continuously so there is no step (see `keyboardHideProgress` in `apps/mobile/lib/manuscript-tab-bar.ts`), or it disappears whenever one of those shows.

An `Animated.FlatList`'s `itemLayoutAnimation` (list-level reflow) must not be left on unconditionally: react-native-screens detaching and reattaching a screen's native view (any push-then-pop, e.g. opening a manuscript's chapters and going back) can replay the layout transition from a stale pre-detach layout, landing real rows collapsed - items vanish with no change to the underlying data. `apps/mobile/app/manuscripts.tsx`'s `layoutAnimating` is the pattern: on for the first reveal and for a render that changes the rows while the screen is focused (`useIsFocused`), off while blurred and on a render whose rows are unchanged, with rows that arrive while blurred never sliding in.

A shared-title morph (`lib/shared-title-morph.tsx`, see `manuscripts.tsx`'s row → chapters-header title) listens for the stack pop with `navigation.addListener("beforeRemove", ...)` to play its reverse animation. A header several navigators below the one performing the removal (the manuscript's chapters screen sits under its own `project/[id]` Stack, itself nested in a `(tabs)` Tabs navigator) never sees that event on its own `useNavigation()` - only the navigator that actually owns the removal does (`ownsStackRemove` in `stack-pop.ts`). `MorphHeaderTitle` listens on every ancestor up to the root and lets each one's own `ownsStackRemove` check decide, the same pattern `StackPopTransition` uses by having one instance per nesting level.

## Mobile press feedback

Every button answers a finger through one engine, `apps/mobile/lib/use-press-feedback.ts` (tokens in `lib/motion.ts`: 90ms in, 180ms out, scale `PRESS_SCALE`, dim `PRESS_DIM`). `TapPressable` and `PressableCard` are its consumers, and so is any custom surface that needs it: call `usePressFeedback({ feedback, scale, dim, restOpacity, tint })` and merge `animatedStyle` after your own style (`dim: 1` keeps the dip without the dim, as `ThemeCard` does so its swatch stays true). Use `TapPressable` for a button, never a raw `Pressable` with a `({ pressed }) => ...` style (`TapPressable`'s `style` has no function form, so TypeScript rejects it there). Pick `feedback="scale"` (default) for anything with a surface, `"dim"` for a bare text link or icon, `"none"` for a scrim, and `highlight` + `feedback="none"` for a full-bleed list row. `haptic="select"` is for choosing among options, `"none"` when the handler fires its own haptic (never tap twice). A choice control uses `SelectChip` (crossfade and pop via `useSelectionPop`), not a hand-cut selected style. Reduce motion drops the scale and keeps the dim and tint.

## Motion: prefer completable animations

Reach for animation that has a visible beginning and end the person can complete (a ring that closes, a tick that draws, a thread that fills, a line that finishes typing) over open-ended step-to-step indicators (dots, spinners, bare counts). Onboarding's progress thread was chosen because it is the only option that starts empty and ends complete; dots only went step to step, and a count never makes you want to finish. When adding or touching motion, look for the completable form first: `ProgressRing` and `DrawCheck` are the building blocks, and a finished act (goal met, sprint over, export ready) should land on a closed ring or a drawn tick, not on a stopped spinner. No streaks or loss framing anywhere: writing frequency is a calm count of days written (`lib/writing-frequency.ts`).

## Word goal and reminders are optional

Nobody needs a daily word goal. Settings' "Goals and reminders" is three plain rows (Word goal, Writing reminders, Writing history), each opening its own screen (`app/word-goal.tsx`, `writing-reminders.tsx`, `writing-history.tsx`); nothing is adjusted inline. The goal is on by default but can be turned off: "No goal" is `showDailyGoal: false`, which keeps the stored `dailyWordGoal` only as the number the next goal starts from, so anything goal-dependent (the writing meter, widget, a reminder skipped on a met day) reads `activeDailyGoal(settings)` (`lib/app-settings.ts`, 0 = none), never `dailyWordGoal`. A reminder's own `wordGoal` is `number | null` and independent of that setting: null saves and notifies ("Time to write") with no count, and the onboarding reminder step saves that way by default.

## Store review prompt (mobile)

`apps/mobile/lib/review-prompt.ts` asks for the native review sheet (`expo-store-review`) once per device, ever, across every trigger (`review-prompt-asked` in local prefs, recorded before the request). Triggers call `scheduleReviewPrompt(trigger)`, which waits `REVIEW_SETTLE_MS` and for the app to be in the foreground (a share sheet backgrounds it), never `requestReview` directly: today a finished `exportManuscript` (not a single chapter) and the writing exercise's finish screen (`app/writing-exercise.tsx`, generic over exercises). There is no "mark manuscript complete" action (a chapter's `final` status is per chapter), so export stands in for it. No pre-prompt of our own; a new trigger needs a `review_prompt_requested` `trigger` value in both analytics catalogs.

## Guided writing exercises (mobile)

`app/writing-exercise.tsx` (the manuscripts `+` menu's "Writing exercises", and a link under the empty library's first-manuscript button) is one screen stepping through a list to pick from (skipped by `?id=<exercise id>`), the exercise's intro, an optional settle-in (the page stays shut while a line at a time holds the screen), its writing parts on the real `ChapterEditor` with `typewriter`, and a finish. Exercises are data, not screens: `EXERCISES` in `lib/writing-exercise.ts` (ordered parts with their soft minutes, an optional settle-in, and whether it is `credited`) plus copy under `exercise.items.<id>` in all four locales (title, tagline, intro, `credit`, `settle`, and each part's name / blurb / guide / placeholder / label). A new exercise is an entry and its strings; `__tests__/writing-exercise.test.ts` fails when any locale lacks copy for a part or settle line. Credit a named writer only for an attribution that holds up (the `credit` line names the work, the test pins the names, and `docs/writing-exercises.md` holds the sources and what was left out), and never put an unverified quote in the copy. The soft per-part timer never locks the page, and an exercise with one part leaves no heading behind. The texts live only in that screen's state (no AI, no sync); "Keep as a manuscript" makes a journal manuscript whose one entry holds the paragraphs (`lib/writing-exercise-save.ts`, the ordinary project create and chapter PATCH, no schema change), and the swipe-back gesture is off so closing asks first whenever there is writing that has not been copied (a Keep counts only once the chapter save lands; a retry after a failed save reuses the manuscript it already made). The id is permanent, since analytics carries it (`exercise` on `writing_exercise_started` / `completed`, with a whole-minute length and nothing the author wrote). The pre-signup quiz tells creativity and writer's-block writers these exist (see "Pre-signup onboarding").

## Manuscript deadlines

A deadline is the existing `ManuscriptTarget` row (`wordGoal` for the whole manuscript, `deadline` as YYYY-MM-DD; `/api/projects/[id]/target`, already in D1, deletion and export), edited on `app/project/[id]/deadline.tsx` and summarised by `DeadlineCard` on the chapters tab. Whether it is on track is `src/lib/deadline-pace.ts` (mirrored byte for byte to `apps/mobile/lib/`, `test/deadline-pace-parity.test.ts`): deterministic, no AI, the words a day still needed against the author's average over the 14 finished days before today (their `WritingDay` totals, which span every manuscript, so a writer with several manuscripts reads as faster than they are on this one). Words come from the open manuscript, not the server's stale total (`lib/use-deadline.ts`, which also plays the once-per-target goal-met moment). Notifications for a deadline would join the writing reminders (`WritingReminderSync`) or go through `sendPushToUser`; none exist yet. The web's surface is `Deadline` in the top bar's More menu (`DeadlinePanel`, a drawer) plus `DeadlineCard` at the head of `ChapterSidebar`, both fed by one `useDeadline(projectId, liveWords, signedIn)` in `src/lib/use-deadline.ts` and hidden in local single-author mode (a deadline belongs to an account); its English copy is `src/lib/deadline-view.ts` (the web has no i18n layer), written to read exactly as the phone's `deadline.*` strings, and removal goes through `useSnackbar` Undo (the server hears only once it lapses; a save made meanwhile cancels the pending delete).

## Mobile themes and fonts

The phone's themes live in `apps/mobile/lib/theme.ts` and `DEFAULT_THEME` ("ciciro", the web's Archive look) is the fallback everywhere. Stored theme ids are permanent: renaming a theme changes only its label (`THEME_META` and the `themes.*` keys in all four locales), never its id. The theme setting syncs to the server and web, so `src/lib/theme.ts` lists the phone-only ids (`PHONE_THEME_IDS`): the server stores them as sent and the web renders its own default of that mode through `webTheme`. A new phone-only theme goes in both lists. The server's "parchment" for an account that never saved settings is not a pick: `GET /api/settings` and `/api/auth/me` report `settingsSaved`, and `withPhoneDefaultTheme` (`apps/mobile/lib/app-settings.ts`) shows the phone default only when that is `false`, never when it is unknown.

The chrome fonts (Newsreader, Instrument Sans, JetBrains Mono) are embedded at build time by the `expo-font` plugin in `app.json`, so a font change needs a new native build and `fonts.*` use a different native name per OS (iOS PostScript name, Android file name). `fonts.serif`, the manuscript's own face, is separate.

## Mobile haptics

Every haptic goes through `apps/mobile/lib/haptics.ts`, never `expo-haptics` directly, so the device-local Settings switch (local prefs like focus mode, default on) silences all of them. Buttons and pills use `TapPressable` (`apps/mobile/components/TapPressable.tsx`), and other shared pressables (`PressableCard`, Settings rows) wrap their handler in `withTap`; the chat stream ticks via `createWritingTicker` and ends with `success()`/`warning()` in `use-ciciro-chat.ts`. A completion moment (goal met, sprint finished) uses `haptics.celebrate()`, never a hand-rolled pair of haptics.

## Mobile screen error recovery

A mobile screen whose content comes from a query (not a one-off action) renders its failed/empty state with `ScreenErrorState` (`apps/mobile/components/ScreenErrorState.tsx`), never a bare error `Text`: a friendly message, Try again, and Restart app (`apps/mobile/lib/app-restart.ts`'s `restartApp`, offered only once a retry has already failed) with the server's raw text behind a "Details" toggle rather than in the headline. Wrap the screen's default export in `ScreenErrorBoundary` so a render crash gets the same recovery UI instead of a dead screen. A background refetch failure must not blank a screen that still has cached data to show - keep showing it next to an inline (`variant="inline"`) banner, same as `manuscripts.tsx` and the chapters tab do; reserve the full (`variant="full"`) state, as the list's `ListEmptyComponent`, for when there is nothing cached. Pull-to-refresh stays wired regardless of error state.

## Mobile accessibility

iOS ignores `role="alert"` and `accessibilityLiveRegion` on content that appears, so status text that lands off-focus is spoken with `announce()` (`apps/mobile/lib/announce.ts`). Error text uses `AlertText`, which announces itself. Touchables default to the button role (`TapPressable`, `PressableCard`), so pass `accessibilityRole` only to override it. Text colours must clear 4.5:1 and text-field outlines 3:1 on every theme: the `field` token exists for that, and `__tests__/theme.test.ts` fails when a palette drifts below it.

## Android specifics (mobile)

Check a mobile change on an Android emulator too (`docs/android-walk.md`); four things differ from iOS. Fonts: `fonts.serif` / `fonts.sans` name the generic `"serif"` / `"sans-serif"` families there, since Georgia does not exist (a missing name silently falls back to sans). Blur: `expo-blur` blurs only inside a registered `BlurTargetView`, so a `BlurView` on Android does nothing and a translucent floating surface shows the page through it; gate blur on `BLUR_SUPPORTED` and wash with `glassWashAlpha` (`lib/blur-support.ts`, fully opaque on Android). Keyboard: a floating IME add-on (voice typing's strip, the stylus toolbar) reports `isVisible` while covering nothing, so lay out around the keyboard with `useCoveringKeyboard` (`lib/use-covering-keyboard.ts`) or `isRealKeyboard(height)`, never a bare `useKeyboardState(...isVisible)`. Switches: a dark theme's thumb is its ink colour (`lib/switch-theme.ts`).

## AI-involvement tally

`Chapter.aiAcceptedWords` / `aiDraftedWords` (see `src/lib/text.ts` `aiInvolvement`) are cumulative counters, not derived from `content`: accepting a Ciciro suggestion drops its authorship marks (`resolveSuggestions`), so the word count has to be taken at that moment (`ciciroAcceptedWordCount` in `src/lib/suggestions.ts`, called from every accept path, web and mobile) and added, permanently - a later edit or deletion never moves or removes it. The same applies to text Ciciro inserts with no suggestion to accept (`insert_text`, a chat `<draft>` paste): tallied once, at insertion. The percentage's denominator, `wordsAdded`, is tallied the same way inside the op log's commit (`tally` in `src/lib/chapter-ops.ts`): a server-side writer that lands new Ciciro prose passes `tally: "drafted"`, one that restores old text passes `"none"`. Do not try to reconstruct any of these from `content` later.

## Craft defaults

Craft defaults (`src/lib/craft-defaults.ts`, see `docs/craft-defaults.md`) are the opt-in "Experimental writing prompt" setting (`craftDefaults`, off by default), and with it off every prompt must stay byte for byte what it was (`test/craft-defaults.test.ts` pins them). A new path that drafts prose reads `proseOptions(projectId)` (`src/lib/craft-options.ts`: the owner's setting plus the `style.md` em-dash switch, which the drafter cannot see), builds its prompt with `drafterSystemFor(kind, { emDashes, craft })`, and only when `craft` is on runs `checkDraft` so the editor gets a CRAFT CHECK. The em-dash switch works with craft on or off. The defaults never apply to the author's own prose.

## Checks with structured findings

A quick action (`src/lib/prompts.ts`) can be `kind: "panel"` instead of the default `"chat"`: `ChatPanel` calls a callback prop instead of sending a chat prompt, so the chip can open a dedicated drawer with its own API route and lib module (see `continuity-check` / `src/lib/continuity.ts` + `continuity-view.ts`, alongside `RepetitionPanel`/`WeeklyReview`) rather than routing through the agentic editor chat. A finding's exact quote becomes a jump-to link by opening `SearchPanel` pre-filled with that text (`onInspect` in `Workspace.tsx`) rather than building new anchor/scroll plumbing. Keep the LLM-facing side of such a check bounded and cheap: one non-agentic `DRAFTER_MODEL` call per unit of work (not the `EDITOR_MODEL` chat loop), sending only the bible files relevant to what's being checked, and re-verify any quoted text is an actual substring of what was sent before surfacing it (a model can still paraphrase despite instructions not to).

## Who-knows-what ledger

`KnowledgeFact` rows (`src/lib/knowledge.ts`) are the source of truth for the who-knows-what ledger; the mirror block in each `characters/<slug>.md` is derived. The four stances and the story-order rules (`inEffectAsOf`, timeline, topic grid) live in `src/lib/knowledge-ledger.ts`, mirrored byte for byte in `apps/mobile/lib/` (`test/knowledge-ledger-parity.test.ts`). A fact holds from its `chapterId` (null: before the story) until `supersededAtChapterId`; "as of chapter N" compares live `Chapter.order` on both ends, so never cache an order. Every reader of the ledger for a chapter (editor context, continuity check, What changed, the chat tools) goes through `factsAsOfChapter`, not `activeFactsForPaths`, which is the chapter-blind current snapshot. The chat's `record_knowledge` / `read_knowledge` / `revise_knowledge` (`src/lib/knowledge-tools.ts`) are bible writes outside `MANUSCRIPT_WRITE_TOOLS` and default to the run's `activeChapterId`, which both clients send with every turn. Details in `docs/story-bible.md`.

## AI allowance and billing

Every AI entry point is metered on a hosted server (`src/lib/entitlements.ts`, see `docs/billing.md`): a user-initiated action claims one run with `meterAiRun` or `withAiRun` (which refunds on failure), and background or free work checks `aiAllowed`/`assertAiAllowed` so it stops at the limit. A new AI route or lib caller needs one of these, or it bypasses the allowance. Billing UI, web and mobile, renders only the server's entitlement, never Stripe or RevenueCat client state.

## Model defaults

`src/lib/anthropic.ts` and `src/lib/fast-lane.ts` pin the models Ciciro runs on; `src/lib/models.ts` resolves them (env override or default) for the `/api/models` endpoint that Settings (web and mobile) reads. Changing a default requires a line in `docs/CHANGELOG.md` recording the new default, since Settings is a user's only visibility into which model they're on.

A model with `thinking` enabled spends its `max_tokens` budget on thinking too, so a cap sized to the expected output can come back with `stop_reason: "max_tokens"` cut off mid-sentence. Any call that writes prose or a plan (`autowrite.ts`, `dispatch_draft` in `tools.ts`) uses `PROSE_MAX_TOKENS` (`src/lib/prompts.ts`) and treats that stop reason, or a safety `refusal` (`stoppedShort` in `src/lib/anthropic.ts`; Haiku 5.5 has no server-side fallback), as a failure, not a finished reply - never persist or hand onward text that stopped there. The same check belongs on any call whose raw text return is committed or cached directly (`recap.ts`'s "Previously on" recap, `summarize.ts`'s chapter summary); a call that instead parses JSON out of the reply (`correct.ts`, `continuity.ts`, `weekly-review.ts`) is already safe, since a cut-off reply fails to parse and falls back.

`src/lib/prompts.ts`'s header comment tracks which per-model tuning notes are still live; re-check it against Anthropic's current migration guidance whenever the pinned model changes. On Opus 5.5+, a between-tool-call note longer than a sentence or two arrives as an otherwise-empty `thinking` block - `editor-run.ts`'s stream loop requests `display: "updates"` (beta `thinking-display-updates-2026-08-18`, only for models `src/lib/thinking-display.ts` lists, retried without it on a 400 naming it) and forwards non-empty `thinking_delta`s as `progress` events so authors see them. `ChatPanel.tsx` (web) and `ciciro-stream.ts`/`CiciroChat.tsx` (mobile) render these as an ephemeral, subtly-styled line, never added to the visible reply or the persisted transcript.

## Stopping an editor run

`POST /api/chat/cancel` (`cancelEditorRun` in `src/lib/editor-run.ts`, see `docs/editor-agent-runs.md`) is the only way to stop a durable run; an aborted client fetch alone never does (the claimed slice keeps running and checkpointing). It is checked at iteration boundaries and before each tool call, never mid-stream or mid-tool, so the run finishes whatever it is currently generating or executing before it notices. Both `ChatPanel.tsx` (web) and `use-ciciro-chat.ts` (mobile) must call it from their Stop control - wiring one without the other leaves that surface with the old "Stop does nothing server-side" bug.

## Analytics

Product analytics (PostHog) sits entirely behind `AnalyticsAdapter`, never a vendor SDK, at any call site (`src/lib/analytics-events.ts`, mirrored byte-for-byte in `apps/mobile/lib/` like `manuscript.ts`/`suggestions.ts` above; `test/analytics-events-parity.test.ts` fails when they drift). A new event needs a typed entry in both catalog files before any `track()` call uses it. Never put manuscript text, chat content, titles, or other author prose in an event or property, and identify by internal user id only, never email or name. See `docs/analytics.md` for the tracking plan and feature inventory, `docs/hosting.md#analytics` for env vars and setup.

Analytics needs GDPR/ePrivacy opt-in consent before it runs at all, per device, never synced (docs/analytics.md's "Opt-in consent" bullet is authoritative). Web asks everyone; the phone asks only where `consentModeFor` (`apps/mobile/lib/consent-region.ts`, location from `GET /api/app/consent-region`, cached by `consent-region-store.ts`) says opt-in (EEA / UK / CH, California, Washington, Oregon, and anywhere unknown) and defaults analytics on elsewhere in the US, so mobile code asks `effectiveAnalyticsAllowed({ record, mode, ... })` / `useAnalyticsAllowed()`, never the record or the account flag alone. The prompt copy promises the data is never sold or shared for advertising: keep it true to the actual recipients (docs/analytics.md). Mobile: `apps/mobile/lib/consent.ts` (the versioned record and `effectiveAnalyticsAllowed`), `ConsentGate`/`app/privacy-choices.tsx`/`components/PrivacyChoices.tsx` for the prompt and its Settings entry point, and `apps/mobile/lib/analytics-client.ts` for the gating - the real posthog-react-native client is never constructed before consent, and every construction defensively calls `optOut()` first because the pinned `posthog-react-native@^4.78.4` lacks the upstream `persistOptOut` fix for a native/JS opt-out race (PostHog/posthog-js#4973); check whether a later bump has it before removing that defensive call. Web: `src/lib/consent.ts`/`consent-cookie.ts` (the same versioned record, in a first-party `ciciro_consent` cookie read server-side in `layout.tsx` so the banner never flashes on reload), `ConsentProvider.tsx`/`CookieConsentBanner.tsx`/`CookiePreferencesDialog.tsx`/`CookieSettingsButton.tsx` for the prompt and its reopenable preference center, and `src/lib/analytics-client.ts`/`analytics-posthog-web.ts` for the gating - posthog-js is never initialized with capturing on by default, and withdrawal sweeps every `ph_*` cookie/localStorage key outright. Both platforms' `app-settings.ts`/`settings.ts` `analyticsEnabled` is the signed-in account's synced half of the same decision (defaults to `false`) - effective analytics needs the device *and* that account flag to agree once someone is signed in.

## SEO: sitemap, robots, canonicals, structured data

`src/app/sitemap.ts` and `robots.ts` are Next's file-convention metadata routes, so a new one needs a `PUBLIC_PATHS` entry in `middleware.ts` (`/robots.txt`, `/sitemap.xml`) or it 307s to `/login` like any other unauthenticated request to a non-public path in a hosted deployment - the same trap `opengraph-image`/`twitter-image` routes hit (see "Link previews" below). `sitemap.ts` only lists the pages meant to rank (not `/about`, which is `/`'s content under its own canonical, and not `/launch`, a permanent redirect to `/`); a new public marketing page goes in both `sitemap.ts` and `PUBLIC_PATHS`. Every public page's `metadata`/`generateMetadata` sets `alternates: { canonical: "/path" }`; auth/utility pages with no unique content to rank (login, signup, forgot/reset-password, verify-email, email preferences) set `robots: { index: false }` instead. `src/lib/structured-data.ts` holds the JSON-LD builders - `organizationJsonLd`/`websiteJsonLd` render once, globally, in the root layout; `breadcrumbJsonLd` and `softwareApplicationJsonLd` are per-page (see `pricing/page.tsx`, built from the same live Stripe prices the page already fetches, never hand-entered numbers). `src/lib/public-origin.ts`'s `SITE_URL` is the one constant for a build-time site origin (no request to read a Host from) - `metadataBase`, `sitemap.ts`, `robots.ts` and `structured-data.ts` all read it rather than re-deriving `CICIRO_PUBLIC_URL` with their own fallback. `middleware.ts` 308-redirects any `www.` host to the apex (`ciciro.app`), since `wrangler.jsonc` routes both hostnames to the same Worker and search engines need one canonical host, not two serving identical pages.

## Link previews (Open Graph / Twitter cards)

Every public page's preview image is `ImageResponse` (`next/og`), never a static PNG: `src/lib/og/` holds the shared pieces (`brand.ts` colors/size, `fonts.ts`, `BrandMarkOg.tsx`, `OgFrame.tsx` for the shared paper-and-border scaffold (mark, wordmark, accent rule - no footer line; small secondary text is unreadable once a card is shown at phone width, roughly a 0.3x scale), `generic-image.tsx` for the one brand image `/`, `/features`, `/changelog`, `/privacy` and `/terms` all re-export via their own `opengraph-image.tsx`/`twitter-image.tsx`, `share-image.tsx` for the dynamic manuscript-share preview). This runs on the Node.js runtime (`export const runtime = "nodejs"` on every image route) - `@opennextjs/cloudflare` has no edge runtime at all, but `ImageResponse` on Node works unmodified on the Worker deploy. Satori (what `ImageResponse` draws with) reads ttf/otf/woff only, not the woff2 `next/font/google` serves the app itself, and can't resolve a variable font's weight axis - `public/fonts/newsreader/` and `public/fonts/instrument-sans/` are static weight instances pre-cut from the same upstream variable fonts with `fonttools varLib.instancer`. **`fonts.ts` reads those files through the Worker's `ASSETS` binding (`env.ASSETS.fetch(new Request("https://assets.local/" + path))`), not `node:fs`** - `fs.readFile` throws "no such file or directory" for anything under `public/` on the deployed Worker even with `nodejs_compat` (confirmed by deploying and fetching the route, not by assumption; `public/` is served through the separate ASSETS mechanism, not a readable filesystem). `node:fs` is kept only as the fallback for a plain Node.js host (`next build && next start`, where there is no Worker context to detect - see `workerAssets()`'s `Symbol.for("__cloudflare-context__")` lookup, the same one `src/lib/db.ts` and `src/lib/d1-binding.ts` use for D1). **Any new Next.js file-convention image route needs a middleware allowlist entry** - `src/middleware.ts`'s `isPublic()` matches any path ending in `/opengraph-image` or `/twitter-image`, because a link-unfurling bot has no session and `CICIRO_REQUIRE_AUTH=true` in production redirected every one of these to `/login` until that rule was added (caught by fetching the routes on an actual Workers-runtime preview, not local `next start`, which has no auth-gating middleware difference to catch it). `metadataBase` is set once in the root layout so every image route resolves to an absolute URL. **`overflow: hidden` does not reliably clip in Satori** the way it would in a browser: a flex-grow child needs an explicit `minHeight: 0` (`OgFrame`'s content wrapper) just to respect its flex-computed size instead of growing to fit content, and even with that, a child taller than its row's actual available space (see the git history of `main-option-c.tsx`'s phone mockup) can still bleed past the frame and off the canvas - size content to the space that's actually there (do the arithmetic, verify by rendering) rather than trusting clipping to save you. A share link's preview text ("{author} is sending you their {kind} {title}") is `src/lib/share-preview.ts` + `shares.ts`'s `sharePreviewInfo`, which returns null (generic image, no leak) for anything not currently active - a revoked/expired/unknown link must never render differently from a never-issued one; since the author/title are user-written and can run long, `share-image.tsx`'s `bigFontFor` steps the font size down for a long pairing rather than assuming a fixed size always fits. Local verification of any of this needs the actual Workers runtime (`npm run cf:preview`), not `next start` - the two diverge exactly on the things that matter here (`node:fs`, the ASSETS binding, auth middleware in a hosted config).
